## 3. Findings

### Template defects found by using it

| # | Finding | Effect | What the trial did |
|---|---|---|---|
| 1 | The Python runner ends with `os.execv`. On Windows that returns exit code 0 at once and leaves the suite running detached | A failing suite looks green. The gate does not hold | Runs behave in the same process. This also lets coverage see the product |
| 2 | `openspec validate --strict` rejects the template's own fenced Gherkin: it wants `- **WHEN**` bullets | The task template's "validate --strict before archive" cannot pass | Validates without `--strict` |
| 3 | Text above the first section of a spec is dropped at archive | The spec rule "explain a term the first time" has nowhere to go | Terms are explained inside the requirements |
| 4 | `mutmut` does not run on Windows | One of the four end-of-change checks is missing on this machine | Left out; needs WSL or CI on Linux |
| 5 | The specs-and-code zone rule puts `adr/` in the code zone and the ADR manifest in the specs zone | One ADR step needs two commits | Two commits |
| 6 | Skill links check out as text files on Windows | Skills do not load in a new worktree until a script is run | Not needed here: the skills were read as files |

### What the trial says about the assessment's predictions

| Prediction (assessment §3) | Result |
|---|---|
| The first change is the most expensive | True. About half the code written is the acceptance project and its support |
| Spec rules will not fit a developer platform | Did not bite at this size. All seven scenarios read as things a person does. It will bite at the engine boundary and the store, which had no scenario here and went to the design and ADRs |
| Every scenario pays the start-up cost | True but small so far: under 2 s per flow run, 17 s for the suite |
| Mutation testing will be slow on Docker-backed tests | Not tested: the tool did not run at all |
| Autopilot is the right default | Supported. The planning took minutes because nothing waited. The unanswered question is whether the sponsor would have changed any of the 8 decisions |

### What the executable spec bought

- The scenario "Nothing changed, nothing written" decided the sink's design: it had to count changed rows, not rows sent.
- The runner defect (finding 1) was caught because a suite that could not pass reported success. Under the pilot's process that would have been a green CI run.
- 96% of lines were reached by the scenarios alone. The remaining 4% were the errors a person meets before a run starts, which the specs do not yet promise.

## 4. Where the trial did not follow the process

| The process asks for | The trial did | Why |
|---|---|---|
| A GitHub issue first | The issue text is a file in the change | The sponsor chose to keep the trial on a branch |
| The owner reviews each planning artifact, one decision per question | All five written in one pass, each its own commit | The sponsor's instruction to continue; review is at the end |
| An independent reviewer checks the specs for overlap and gaps | Not done | No subagents in this project's working rules |
| Autopilot: one subagent writes tests, another the code | One session wrote both, tests first | Same |
| One red and green per step definition | All 17 steps written, one red; then the product, one green | Autopilot; the single red still failed for the right reason |
| A mockup, then an independent UI verifier at 1280 pixels | Not done. The dashboard is checked by its page object only | Needs a subagent, and nobody has looked at the page |
| Review videos, then archive | Not done | The owner has not reviewed |

The dashboard page has not been seen by a person or in a browser. Its content is tested; its appearance is not.

| | Pilot, first stage | Trial change |

| Weakest point | Nothing tied docs to tests | A broken runner could have made every check meaningless, and the process had no check for the checker |

## 6. Recommendation

Go ahead with option B, with four changes to the setup before the second change:

1. Fix the runner for Windows in the template itself (finding 1), not only in this project.
2. Drop `--strict` from the task template, or teach the extractor to satisfy it (finding 2).
3. Run mutation testing in CI on Linux, not on the developer's machine (finding 4).
4. Add a check that the acceptance suite can fail: one scenario that is expected to fail, run in CI.

Still open for the sponsor: review the 8 design decisions and the dashboard page, and decide whether usage errors
(a missing setting, a missing flow file) should become promises in the spec.
