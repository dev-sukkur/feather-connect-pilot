Feather Connect Code Guide

What each folder and file does, what to read first, and what is left to build. It describes the stage-3-reliability branch. Stage 2 merged as PR 3. The sections on the core loop keep their line counts from Stage 1, so those counts are approximate now.

The project now has four packages: feather-connect (the SDK and runtime), feather-engine-dbos, feather-server and feather-cli. There are about 1,370 tests, plus crash, latency and engine conformance suites. A flow runs on Postgres and DBOS and shows in a dashboard. Stage 3 proved crash safety and added webhooks, the sealer and pollers. Paths in the sections below are under packages/feather-connect/.

Suggested reading order

  1. See what a flow author writes: tests/testing/test_harness.py. The test at the end is the design's §5.7 example.
  2. Learn the model: core/records.py, core/dataset.py, core/flow.py.
  3. Read the highest-risk code: runtime/extract.py, then runtime/apply.py. A bug here can lose or duplicate data.
  4. See how it is wired: runtime/runtime.py and engine/port.py.
  5. Check the guarantees: storage/port.py and tests/runtime/test_seal.py.

Priority labels: Read closely can lose or duplicate data. Read shapes the public API or later plans. Skim is small or support code.

How a run works

start_run runtime/runtime.py creates the run record, submits the plan task feather.plan runtime/plan.py chooses which partitions to read feather.extract runtime/extract.py reads the source, finds changes, writes chunks to the spool feather.seal_run runtime/seal.py only for multi-slice runs: decides deletes, seals together feather.apply runtime/apply.py delivers each sealed version to each route, in order, through the ledger

Each step runs as an engine task, through the Engine port. Data stays in the spool, and tasks carry ids only.

Known gaps

Stage 3 added these files: runtime/sealer.py (groups webhook events into versions), core/webhooks.py (signatures), feather_server/ingress.py (the webhook endpoint and its queue), migrations 0005 to 0009 (writer claims, the inbox and its holds, stream runs), and the test suites tests/chaos, tests/perf, tests/engine_conformance and tests/e2e/test_webhook_latency.py, with shared helpers in tests/support/real_stack.py.

  • Open review findings: S5, S6 and 14 minor items from the Stage 3 review, and 13 from Stage 2, are listed in docs/04-plan/README.md.
  • Exactly once needs the sink's help: a delivery can repeat after a crash, with the same idempotency key. The test sinks honour it in memory only; the Stage 4 connectors must honour it durably.
  • Webhook events: reprocessing or releasing a quarantined event is a service call, with no dashboard button yet. A failing event holds its dataset for up to about 5 minutes of retries.
  • The long test run: never hung again in ten runs after leaked pools were fixed, but the cause is unproved.
  • Moves without keep_state: a record moving between slices read in separate runs can be deleted at the destination. Flow.validate warns about this.
  • Multi-chunk replace: a sink rejection partway through can leave the destination partial. The delivery fails and says so.
  • Source with a key in two slices: with keep_state, it re-sends every run. M2 must guard this before side-effect routes.
