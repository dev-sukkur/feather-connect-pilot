# M3.1 plan 1: every discovery flow scenario, read-only AI, and the pilot

[M3.1](milestones-and-scope.md#6b-m31-flows-read-only-ai-and-the-pilot), as the sponsor scoped it on 13 Nov 2026. v1.0.0
is on hold while Feather runs privately on Railway (`deploy/railway/`). M3.1 does two things before that pilot: it
builds what discovery's flow scenarios still need, so that every one of them can run, and it adds what a pilot needs
to be watched and judged. It also adds an AI that can **check** things and change nothing.

Requirements:
- **FR-C2:** SQL transforms over versions, on embedded DuckDB.
- **FR-C4:** derived datasets, recomputed on a schedule.
- **FR-C5:** cached reference lookups.
- **FR-D5's second half:** connection availability windows. Pause and resume came in M1.
- **FR-L1's read half**, and the parts of its author half that change nothing. The act tools stay in M8.
- **FR-M3's "agent down"**, as a rule for when no worker is alive.

These come out of M4 and M8.

## 1. What is there already

| Piece | State |
|---|---|
| Transforms | A record map (`map=fn(record, ctx)`) and a batch map over Arrow (`@fc.batch_map`) on each route (`fc.to`), applied in `core/transforms.py`. A transform must be deterministic; each delivery attempt records the code version |
| Datasets | `fc.Dataset(name, source=, key=, strategy=, partition=, keep_state=, …)`. `keep_state=True` keeps the latest state of every record in the store. Strategies: `by_stamp`, `snapshot_diff`, `replace`, `push` |
| DuckDB | The `feather-duckdb` connector: DuckDB and MotherDuck as a source (a query) and a sink. A warehouse view can already be diffed and pushed (`snapshot_diff` over a DuckDB query: UC-06's mechanism). What doesn't exist is a query over **Feather's own datasets** |
| Waiting visibly | A delivery that would overspend a budget raises `BudgetDeferred`, and `note_wait` records "waits for budget B until T" on the run's timeline (H8). Readiness gates a run until its inputs are complete (M2) |
| Triggers | `fc.cron(expr, tz=)`, `fc.every`, `fc.manual`, `fc.on_event`, `fc.on_ready` |
| Alerts | Rules `run_failed`, `delivery_failed`, `budget_high`, `hold_waiting`, `schedule_skipped`, `dataset_stale`. Channels webhook, Slack and SMTP. Evaluated by a server loop. **No rule fires when no worker is alive** |
| Read API | `GET /api/v1/` flows, runs, a run's tasks and records, task logs, holds, partitions, versions, records and diffs, record traces, deliveries, alerts, budgets and usage, connections, summary. RBAC on every route (the every-route test, M3 X2) |
| Viewer role | `viewer` tokens are refused every state-changing route. They are the default in protected environments (M3 E3) |
| PII | `Dataset(pii=…)` masks fields in the dashboard, API and CLI unless a PII reader asks (M2) |
| AI | `AGENTS.md` in generated projects and JSON output from every CLI command (FR-L2, M1). No MCP server |
| Railway | `deploy/railway/`: the server and the worker on Railway's Postgres. No uptime check; the code version shows as `unknown` |

## 3. Design

### 3.1 SQL transforms and reference lookups (F1)

```python
invoice_lines = fc.to(
    postgres.Table(connection="staging", table="invoice_line"),
    map=fc.sql("""
        select b.*, m.description, m.base_unit
        from batch b
        left join {{ dataset('sap.material') }} m using (material)
    """),
)
```

- **What it is.** `fc.sql(query)` returns a batch map, so it plugs into `fc.to(map=…)` with nothing new in the
  runtime's apply path. The batch is registered with DuckDB as `batch`, an Arrow table, with no copy. The query's
  result is the batch the sink gets. Its key field must survive the query: one that drops it fails as a
  `PermanentError` naming the route.
- **References.** `{{ dataset('name') }}` is replaced by a view over that dataset's latest sealed state, which needs
  `keep_state=True` on that dataset. `feather validate` says so if it is missing, along with an unknown name and a
  cycle. The state is read once per apply task, as of its start, and cached per worker by the reference's newest
  version id (FR-C5's "cached"). A new version replaces the cached copy.
- **Determinism** (design §5.5). The delivery attempt records each reference's version id next to the code version,
  so a delivery can be explained afterwards. A replay uses the references **as they are now**: replaying after a fix
  to reference data is the usual reason to replay. The attempt record shows which versions were used each time.
- **From Python.** `ctx.lookup('sap.material', key)` gives one record or `None`. `ctx.reference('sap.material')`
  gives the whole state as an Arrow table, for a batch map. Both use the same cache.
- **Bounded and shut in.** DuckDB runs in the worker's process, with `memory_limit` from `FEATHER_SQL_MEMORY`
  (default 1 GB) and `enable_external_access = false`, so a query can't read files or URLs. Only `batch` and the
  declared references are visible. A reference bigger than `FEATHER_SQL_REFERENCE_MAX_ROWS` (default 5 million)
  fails the task, naming it. A larger one belongs in the warehouse, read through the DuckDB connector.
- **Packaging.** DuckDB comes with the `sql` extra (`feather-connect[sql]`). The worker image installs it. A project
  that uses `fc.sql` without it fails `feather validate` with the install line.
- **Tests.** Unit tests for the batch map: types, nulls, a dropped key, a duplicated key. A test that the query can't
  reach a file. The FlowHarness with a reference dataset. Hard cases H16 and H17 (section 4).

### 3.2 Derived datasets (F2)

```python
effective_price = fc.Dataset(
    "pricing.effective_price",
    source=fc.derived(
        """
        select item, store, price, valid_from
        from {{ dataset('sap.price') }}
        where valid_from <= current_date
        qualify row_number() over (partition by item, store order by valid_from desc) = 1
        """,
        inputs=["sap.price"],
    ),
    key=("item", "store"),
    strategy=fc.strategy.snapshot_diff(),
)
flow = fc.Flow(
    "effective-price-to-pos",
    reads=effective_price,
    deliver=[fc.to(http.Call(connection="pos", url="/prices/{store}/{item}", method="PUT"), mode="upsert")],
    triggers=[fc.cron("5 0 * * *", tz="Asia/Kolkata"), fc.on_ready(fc.ready("sap.price"))],
)
```

- **What it is.** `fc.derived(query, inputs=[…])` is a `Source`. Its read runs the query on DuckDB over the inputs'
  latest sealed state, the same views as F1, and returns the rows. Everything after the read is what any dataset
  has: `snapshot_diff` turns the rows into a version of upserts and deletes, the spool, routes, the ledger, replay
  and the record trace. A derived dataset can be the input of another one. `feather validate` refuses a cycle.
- **When it is recomputed.** On its flow's triggers. A cron recomputes with no change at the source: that is how a
  future-dated price takes effect on its date. `fc.on_ready(fc.ready(input))` recomputes when an input is complete through a
  period. A recompute that changes nothing seals an empty version and delivers nothing, and the run page says why
  (M2's "read found no new or changed records").
- **Time.** `current_date` and `now()` in the query are the run's scheduled time in the trigger's time zone, not the
  worker's clock, so a re-run of a past day computes that day's answer.
- **Partitions.** In M3.1 a derived dataset is not partitioned: one read covers it all. A partitioned one,
  `{{ partition }}` in the query, waits for a pilot that needs it.
- **Warehouse queries.** A query over the warehouse is already a DuckDB connector source, so `fc.derived` doesn't
  repeat it. Its docs point to it.
- **Tests.** Its reads in the FlowHarness. Hard case H18. UC-06 end to end on Postgres in `tests/e2e`: prices with
  future dates, the clock moved past one, and only the changed price reaching the sink.

### 3.3 Availability windows (F3)

```yaml
connections:
  erp:
    connector: sap-cpi
    windows:
      tz: Asia/Kolkata
      open: ["22:00-05:00"]      # one or more spans; a span may cross midnight
      applies: [read]            # read, write, or both (default both)
```

- **What waits.** A task that needs a windowed connection outside its window doesn't start: an extract reading it, or
  an apply writing to it. It waits until the window next opens. The wait goes on the run's timeline with the
  connection and the time, through the same `note_wait` path as a budget wait, so nothing is silent (FR-E4). A
  scheduled run outside the window is still created, and waits. Manual runs wait too, and the dashboard says so before
  you confirm.
- **What doesn't wait.** Webhook ingress always accepts and spools: a closed window holds back only the delivery. Other
  routes of the same dataset go on (FR-B1).
- **A window that closes mid-task.** A task that started inside the window runs to its end. Windows gate starts, so a
  long read can run past the close. `max_overrun` on the window (default none) makes a chunked read stop at its next
  chunk boundary past it, and resume when the window opens again.
- **Seeing it.** The connection page shows its windows and whether it is open now. The overview counts the tasks
  waiting for a window. `feather validate` checks the spans and the time zone.
- **Pause and windows.** They are separate. Pause is an operator's act with a reason. A window is configuration, in
  git, and can't be overridden at runtime in M3.1 (FR-G4 stays in M4).
- **Tests.** A clock-driven test of spans crossing midnight and of daylight saving in a zone that has it. Hard case
  H19. The chaos suite's kill mid-apply on a windowed sink.

### 3.4 Read-only MCP (A1)

- **Two ways in, one rule.** `feather mcp --server URL` serves MCP over stdio for Claude Desktop or Claude Code on
  a laptop, calling the server's JSON API with the user's token. `POST /mcp` on the server serves MCP over HTTP with a
  bearer token. Both use the official `mcp` Python SDK, and both go through the same service layer, so RBAC and
  masking are the API's.
- **Read only, three times over.**
  1. Only read tools exist.
  2. `/mcp` accepts only a **viewer** token: an operator's or an admin's is refused with 403 and a hint to make a
     viewer token.
  3. The server refuses a viewer's every state-changing call anyway (M3 X2's every-route test).

  `feather server create-token claude --role viewer` makes one. The service already takes `viewer`; the CLI's
  help text, which names only admin and operator, is fixed with A1.
- **Read tools** (design §14.2):
  - `list_flows`, `describe_flow`;
  - `list_runs`, `get_run`, `get_task_logs`;
  - `list_failures`, `list_alerts`, `list_holds`;
  - `partition_status`, `trace_record`, `version_sample`;
  - `budget_usage`, `list_connections`.

  Each wraps one or two JSON routes, with paging, and caps its output (`FEATHER_MCP_MAX_ITEMS`, default 200).
- **Local author tools**, stdio only, with no server: `describe_connector` and `validate_project`, reading the project
  on disk. `run_local` and the scaffolding tools stay in M8: they write files or run code.
- **Untrusted data** (design §14.3). Record values and log lines are wrapped as untrusted content, with a note that
  they are data and not instructions. PII fields stay masked: a viewer is never a PII reader through MCP. Secrets are
  never returned; the API can't return them anyway.
- **Recorded.** Each tool call is written to the audit log as `actor_type=agent`, with the token's name and the tool's
  name. It is rate limited per token (`FEATHER_MCP_RATE_PER_MIN`, default 120).
- **The skill.** `skills/investigate-failure/SKILL.md`, also put into projects by `feather new`. It walks from an alert
  to the run, its task logs, the failing deliveries and a record trace, and ends with what to do and who should do
  it. It never asks for a change, since it has no tool for one.
- **Tests.**
  - The tool list holds no write tool, checked against the API's write routes.
  - Each tool works with a viewer token and is refused with an operator token.
  - Masking and untrusted wrapping.
  - An MCP client over stdio against a test server.
  - The demo's failed delivery is investigated through MCP to its cause, in `tests/e2e`.

### 3.5 Watching the pilot (O1, O2)

- **`worker_missing`.** It fires when no worker has sent a heartbeat for `after` (default `2m`) while the environment
  has a flow that isn't paused, and clears on the next heartbeat. It is critical, on by default, and its subject is
  the environment. A chaos test kills the only worker and sees it fire and clear.
- **Teams.** First a check that a Teams workflow URL takes the webhook channel's JSON. If it doesn't, a `teams`
  channel kind posts a Teams message card: a small addition to `services/alerts.py`. Only if the sponsor uses Teams
  (section 5).
- **The server itself.** Alerts come from the server, so a server that is down sends none. The Railway guide adds an
  external uptime check on `https://<domain>/readyz` every minute, with any uptime service, alerting the same people.
- **The code version.** `FEATHER_CODE_SHA=${{RAILWAY_GIT_COMMIT_SHA}}` on both services, so each run shows the
  commit it ran.
- **Cost.** The guide says where Railway's usage limit and its email alert are set.

## 4. New hard cases

| # | Case | Holds |
|---|---|---|
| H16 | A SQL transform joins a reference that gets a new version while a version is being applied | The apply uses one reference version throughout, recorded on its attempts; the next version uses the new one |
| H17 | A record whose reference row is missing, then added | A `left join` delivers it with nulls, or an inner join filters it, as written; replaying after the reference row arrives delivers it complete |
| H18 | A future-dated price takes effect with no change at the source | Before its date nothing is delivered; on the date's scheduled recompute, exactly that price is delivered once; a re-run of the day delivers nothing new |
| H19 | A read of a connection whose window is closed, with a webhook arriving meanwhile | The read waits, visibly, and runs when the window opens; the webhook is spooled at once and delivered when the sink's window opens; nothing is lost or duplicated |

## 5. For the sponsor (the pilot plan, P1)

These answers go into `docs/07-pilot/pilot-plan.md`.

1. **Flows.** Which flows run in the pilot, on which real systems. For example the reference chain once Q1 gives
   access, and which of Postgres, MotherDuck, Zakya and SAP CPI are real.
2. **How long, and who.** The pilot's length; who operates it day to day; who gets the alerts, and on which channel
   (email, Slack, Teams).
3. **Success.** For example: no lost or duplicated delivery; every failure seen through an alert before a user
   reports it; a failed delivery fixed in under N minutes; the walk-through in at most 5 clicks.
4. **Findings.** Where problems and feedback are written down: GitHub issues with a `pilot` label, or the ledger.
5. **What decides v1.** For example: the success criteria met for N weeks, the findings fixed or accepted, and the
   decisions still open for v1 (Q9 names, Pages, the security findings' written acceptance).
6. **Decisions before real data:**
   - the repository's visibility: it is public today;
   - acceptance of security findings X2-3 and X2-5 to X2-11 for the pilot;
   - whether Railway's daily snapshots (RPO up to a day) are enough, or WAL archiving comes first.

## 6. Exit criteria

- H16–H19 pass, with H1–H15, on Postgres.
- UC-06 runs end to end with a derived dataset: today's effective price to a sink, only the changed prices.
- An MCP session with a viewer token investigates the demo's failed delivery to its cause, and has no way to change
  anything.
- `worker_missing` fires and clears in the chaos suite.
- The pilot plan is agreed, and Feather is running on Railway with an uptime check and alerts reaching someone.
